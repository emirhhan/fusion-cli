# Critical delivery totals in the frontend decoder

The decoder now reads the existing optional `sorun_sayisi`, `criteria_count`,
`criteria_status_counts` and criterion status fields independently of the backend
projection. Empty or truncated detail lists cannot turn a known failure into a
verified delivery card.

- Positive problem or failed totals force `verified: false` and `blocking: true`.
- Unverified criteria, or criteria totals larger than represented outcomes, turn
  an otherwise verified result into `verified: null`. Existing failures and
  blocking remain intact.
- Supplied counts must be nonnegative safe integers. Status totals must contain
  passed, failed and unverified counts. Malformed critical data produces the
  existing invalid envelope, retaining a readable false-claim flag.
- Optional internal totals survive detail trimming and the byte budget. Absent
  optional counts retain compatibility with old journals. Paths and history
  identity rules remain unchanged.

The fixture was generated by the backend projection at commit `550def3f`; tests
compare raw and projected safe, problem, failed, unverified and missing-status
cases. Additional tests cover malformed totals, incomplete coverage, byte-budget
trimming and preserving an existing failure.

Validation: 133 focused decoder, event, card, activity and history tests passed;
TypeScript checking and `git diff --check` passed. The initial decoder regression
run had 18 failing tests before the implementation. No native app, model,
provider or network calls were performed for this follow-up. Parent review of the
combined frontend remains separate from these component checks.
